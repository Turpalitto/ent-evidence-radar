# Промт глубокого аудита: ENT Evidence Radar

> Этот документ — **инструкция-промт**, по которой проводится полный аудит репозитория.
> Он фиксирует роль, границы, методологию, формат находок и критерии готовности, чтобы
> результат был воспроизводимым, проверяемым и приоритизированным, а не списком мнений.
> Результат применения промта — `docs/AUDIT_REPORT.md`.

## 1. Роль и цель

**Роль.** Ты — ведущий инженер-аудитор с тремя шляпами одновременно:
1. *Senior fullstack / SRE* (Next.js App Router, React 19, TypeScript, Drizzle, PostgreSQL/PGlite, Docker, CI);
2. *AppSec-инженер* (OWASP ASVS L1–L2, модель угроз для self-hosted и serverless-деплоя);

**Цель.** Дать владельцу проекта честный, доказательный и приоритизированный ответ на три вопроса:
- **Что исправить** — дефекты, которые уже сейчас приводят к неверным данным, потере данных, дырам в безопасности или отказам;
- **Что улучшить** — архитектурные, качественные и продуктовые слабости, которые ограничивают надёжность, точность и развитие;
- **Что добавить** — отсутствующие возможности, которые закрывают реальные сценарии врача-оториноларинголога и эксплуатации.

## 2. Контекст проекта (что аудируем)

- Агрегатор доказательной ЛОР-литературы: PubMed (E-utilities), Europe PMC, ClinicalTrials.gov v2, medRxiv.
- Ядро: классификация дизайна исследования → уровень доказательности (Oxford 1–5) → индекс доверия 0–100 с расшифровкой; субспециальности; дедупликация; перепроверка ретракций.
- Хранилище: PostgreSQL через Drizzle, по умолчанию встроенный PGlite (файловый, в `./.pglite`).
- Интерфейс: русскоязычный дашборд, лента с фильтрами/поиском, карточка статьи, темы (PubMed-запросы), журнал запусков, статистика, экспорт CSV/RIS/JSON, Atom-лента, email-дайджест, ИИ-перевод/резюме (OpenAI-совместимый API).
- Эксплуатация: Docker (standalone), планировщик в `instrumentation.ts`, внешний cron через GitHub Actions, `API_SECRET` для мутирующих эндпоинтов, CSP через `proxy.ts`.

**Источник истины — код, а не README.** Любое расхождение README ↔ код фиксируется как находка.

## 3. Границы и правила

1. **Доказательность.** Каждая находка подтверждается ссылкой на файл и строку, выводом команды, воспроизведением (curl/тест/проба) или цитатой кода. Гипотезы без подтверждения помечаются «⚠ проверить».
2. **Не выдумывать.** Не приписывать проекту проблем, которых нет; не предлагать переписывание «на модный стек» без конкретной причины.
3. **Внешняя сеть ограничена** (доступны только github.com, registry.npmjs.org, pypi.org). Поведение внешних API (NCBI, Europe PMC, CT.gov, medRxiv, OpenRouter) оценивается по коду и документации; всё, что требует живого вызова, помечается «⚠ проверить онлайн».
4. **Не менять продукт в рамках аудита.** Аудит — чтение, запуск и пробы; временные пробные файлы удаляются. Исправления — отдельная работа по roadmap из отчёта.
5. **Приоритет — риск для врача и для данных.** Неверная классификация доказательности, пропуск ретракции и потеря заметок/закладок важнее косметики.

## 6. Формат находки

Каждая находка оформляется единообразно:

```
ID · Серьёзность · Измерение · Короткий заголовок
Где: путь/файл.ts:строка (и/или компонент)
Доказательство: цитата кода / вывод команды / шаги воспроизведения
Влияние: что ломается и для кого (врач / админ / данные / деньги)
Рекомендация: конкретное исправление (что именно поменять), при необходимости — 2 варианта
Усилие: S (≤2 ч) / M (≤1 день) / L (несколько дней)
```

**Шкала серьёзности**
- **C — Критично:** обход авторизации; потеря/порча пользовательских данных; массовая неверная медицинская информация (ошибочный дизайн/уровень/доверие по систематической причине); неконтролируемые расходы.
- **H — Высоко:** дефект проявляется в типовом сценарии и даёт неверный результат, отказ или заметную деградацию; невоспроизводимая сборка/деплой.
- **M — Средне:** снижает точность/надёжность/производительность в части сценариев; нарушает ожидания, но есть обходной путь.
- **L — Низко:** гигиена, согласованность, косметика, документация.

Находки группируются в три раздела: **ИСПРАВИТЬ** (дефекты), **УЛУЧШИТЬ** (слабости), **ДОБАВИТЬ** (пробелы). Внутри — по убыванию серьёзности.

1. **Резюме для владельца** (10–15 строк): общее состояние, 5–10 главных рисков, оценка по измерениям D1–D10 (1–5) с одним предложением обоснования.
2. **Что уже сделано хорошо** — чтобы не разрушать работающее при исправлениях.
3. **Как проводился аудит** — команды и их результаты, что воспроизведено.
4. **Находки** по формату раздела 6, разделы ИСПРАВИТЬ / УЛУЧШИТЬ / ДОБАВИТЬ.
5. **Roadmap** — спринты с порядком работ и зависимостями (например, «переклассификация базы» должна идти после фиксов классификатора).
6. **Приложения** — команды воспроизведения, список проверенных файлов, что помечено «⚠ проверить онлайн».
