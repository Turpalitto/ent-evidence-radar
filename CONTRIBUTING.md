# Как участвовать в разработке

Спасибо за интерес к ENT Evidence Radar. Этот документ — про то, как устроена разработка,
чтобы изменения проходили ревью с первого раза. Архитектура описана в `docs/ARCHITECTURE.md`,
API — в `docs/openapi.yaml`, безопасность — в `SECURITY.md`.

## Окружение

- Node.js ≥ 22 (как в CI и Docker-образе), `npm ci` для установки зависимостей.
- `cp .env.example .env` — без переменных приложение стартует на встроенной PGlite (`./.pglite`)
  и считается работающим в доверенной сети (нет `API_SECRET`). Для проверки авторизации задайте `API_SECRET`.
- `npm run dev` → http://localhost:3000. Внешние источники (PubMed, Europe PMC, ClinicalTrials.gov,
  medRxiv, Crossref) нужны только для реального сбора; тесты сеть не используют.

## Перед PR

```bash
npm run check   # ESLint → tsc --noEmit → drizzle-kit check → Vitest
npm run build   # то, что соберёт CI (опционально, но полезно при изменениях в app/)
```

CI (`.github/workflows/ci.yml`) гоняет то же самое плюс `npm audit --omit=dev` и smoke-тест Docker-образа.
Шаблон PR содержит чек-лист — пройдите его честно, он короткий.

## Соглашения

### Код
- TypeScript strict, без `any` (eslint это отследит); серверные помощники — в `src/lib`, доступ к БД —
  через drizzle в `src/lib/queries.ts`/`refresh.ts`, не из компонентов.
- Файлы маршрутов `src/app/**/route.ts` экспортируют **только** обработчики и конфиг Next; общая логика
  выносится в `src/lib` (иначе падает проверка типов Next 16).
- Комментарии и тексты интерфейса — на русском; идентификаторы — на английском. Комментарий объясняет
  *почему*, а не *что*.
- Форматтер в проекте не используется — соблюдайте стиль соседнего кода (`.editorconfig` задаёт базу).

### База данных и классификатор
- Любое изменение `src/db/schema.ts` → `npm run db:generate` → просмотреть SQL в `drizzle/` →
  закоммитить вместе с `drizzle/meta`. Миграции не редактируются задним числом; снапшоты не перегенерируются.
- Изменили эвристики `src/lib/evidence/classify.ts` или справочники (журналы, издатели руководств) →
  увеличьте `CLASSIFIER_VERSION`: при следующем запуске записи с меньшей версией переклассифицируются сами.
- Ручные правки пользователя (`manual_overrides`) всегда поверх автоматической классификации — не перезаписывайте их.

### API
- Новые/изменённые маршруты описываются в `docs/openapi.yaml`; контракт-тест (`src/lib/openapi.test.ts`)
  сверяет пути, методы и `$ref`. Тела запросов валидируются zod через `parseBody`, ошибки — через `apiError`/`apiFailure`.
- Изменяющие и дорогие маршруты — только под `checkApiAuth`. Публичные читающие маршруты
  используют `src/lib/public-api.ts` (ETag/304, мягкий rate-limit).

### Тесты
- Vitest; `src/**/*.test.ts(x)`. Чистые функции — юнит-тесты; всё, что трогает БД, — интеграционные
  тесты на PGlite in-memory (см. `refresh.integration.test.ts`, `trials.test.ts`); компоненты — jsdom +
  Testing Library с директивой `// @vitest-environment jsdom` и `mockFetch` из `src/test/fixtures.ts`.
- Адаптеры источников тестируются на фикстурах реальных ответов; сеть в тестах запрещена — мокайте
  `fetchJson`/`fetch` (у Crossref `fetch` инжектируется параметром).
- Для PGlite-тестов с несколькими полными запусками указывайте таймаут явно (`it(..., 20_000)`).

### Коммиты и ветки
- Одна задача — один PR; заголовок коммита в повелительном наклонении, с префиксом пункта аудита/issue,
  если он есть (`A-08: отслеживание КИ — …`).
- Пользовательские изменения — строка в `CHANGELOG.md` (раздел «Неопубликовано»/текущая версия);
  новые переменные окружения — в `.env.example` с комментарием и в README.
